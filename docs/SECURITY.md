# Security notes

- **Untrusted input**: type from magic bytes, never client MIME/extension; size/count/field limits in multer; options re-validated server-side with Zod; PDFs parsed structurally before use; encrypted PDFs rejected with a clear code.
- **Filenames**: client names are sanitized for display/headers only; on disk everything uses random ids. Traversal tested.
- **Isolation**: each job has a private 0700 directory; engines run via `execFile` (no shell), minimal env, cwd = job dir, hard timeout, kill on cancel. Run the API container with the compose hardening (read-only FS, no caps, pids/mem/cpu limits) — this is the real resource-limit boundary; Node does not enforce per-process memory for child engines.
- **Authorization**: opaque httpOnly guest cookie identifies owner; non-owners get 404 (no job-id probing). Downloads need an HMAC-signed, expiring token (issued only to the owner) **and** ownership. Tokens are stripped from logs.
- **CSRF**: cookie is `SameSite=Lax`, CORS is an explicit allowlist, state-changing routes are not reachable via simple cross-site form posts with cookies. Re-evaluate when session auth (accounts) is added.
- **Known gaps**: no AV scanning; pdf-lib loads whole files into memory (bounded by MAX_FILE_MB); in-process queue shares the API process's event loop for pdf-lib work; no per-IP storage quota; dependency audit not yet automated in CI.

## Phase 5 additions
- **Office conversion** runs LibreOffice, a large attack surface. Files are type-checked by content (OOXML package structure / OLE header, entry names only — nothing inflated), converted in a per-job profile with a hard timeout and no shell. Treat the container as the boundary: no network egress for the API container is recommended. Macros are not executed in headless conversion.
- **Passwords** (protect/unlock) travel in the multipart `options` field over TLS, are used in-process only (never on a command line), are stripped from the job record when processing ends, and never appear in logs.
- **Unlock** never attempts to guess or bypass; wrong password → generic error, no output file. Requires an explicit authorization confirmation.
- **Redaction** deletes content by rasterization; verified that the covered text is absent from file bytes and extraction. Do not use *Crop* or the Edit tool's rectangles to hide data — they only cover it (the UI says so).
- **Compare** HTML report escapes all document text.
- **Annotations** are validated server-side against a strict Zod schema (counts and ranges bounded); images are re-embedded by pdf-lib, never passed to an interpreter. ImageMagick only ever processes PNGs we generated ourselves.

## Phase 6 additions (accounts, quotas, billing, admin)
- **Passwords**: scrypt (N=2^15, r=8, p=1) with per-user salt, Unicode-normalized; verification is constant-time and a dummy hash is checked for unknown emails so timing does not reveal accounts. Repeated failures lock the account for 15 minutes (stored in the database, so it survives restarts and works across instances).
- **Tokens**: access JWT (HS256, 15 min, iss/aud checked) lives only in JavaScript memory — never localStorage — so XSS cannot steal a long-lived credential. The refresh token is an opaque random value in an httpOnly, SameSite=Strict cookie scoped to `/api/auth`; only its SHA-256 is stored. Every refresh rotates it; presenting an already-used token revokes the whole session family; two concurrent refreshes cannot both succeed (atomic claim).
- **CSRF**: refresh/logout require a custom header that cross-site forms cannot send, on top of SameSite=Strict and the CORS allowlist. Other endpoints authenticate with the Authorization header, which browsers never attach automatically.
- **Authorization**: the user (and role) is loaded from the database on every request — a demoted or disabled admin loses access immediately even if their token has not expired. Admin routes require `role=admin`; admins cannot demote/disable themselves. Admin job listings omit paths, filenames and options.
- **Quotas**: enforced before the upload is read. Guest quotas count both the cookie and the client IP (clearing cookies does not reset them) — set `TRUST_PROXY` correctly behind a proxy or all guests share one IP. Concurrency limits use the database count.
- **Billing**: webhook route is mounted before body parsing and verifies Stripe's signature over the raw bytes; events are processed once (unique event id; a failed handler releases the id so Stripe retries). An unmapped Stripe price never changes a plan. Entitlement follows subscription status (`past_due` keeps access during retries; `canceled`/`unpaid` returns to Free). No card data ever touches the server. No "fake payment" path exists in any environment.
- **Open redirects**: `?next=` after sign-in is validated to same-site absolute paths; React Router was upgraded to a patched major.
- **Password reset**: single-use, 1-hour token, only its hash stored; all sessions revoked on reset or password change.
- **Multiple instances**: API replicas and workers can share one MongoDB, Redis and storage volume. Startup no longer wipes or fails anything: unknown directories are removed only after a 10-minute grace period, and crashed work is recovered by the heartbeat reaper (see Phase 7). (Earlier versions required exactly one instance per storage volume.)
- **Known gaps**: no per-account storage quota, audit log has no integrity protection, admin settings changes are not versioned.

## Phase 7 additions (isolation, abuse resistance, verification)
**Defence in depth for untrusted documents** — each layer assumes the previous one failed:
1. *Validation*: signature-based type detection, size/part/field limits, strict option schemas, pixel-count guard on images (100 MP) before any decoder runs, page limits, malformed multipart → 400 (never 500).
2. *Process isolation*: every job runs in **its own process and process group** (`processToolIsolated`) under kernel limits set with `prlimit`: address space (`RLIMIT_AS`, covers Buffers/typed arrays — a V8 heap cap does not), CPU seconds, and maximum file size. A decompression bomb gets the *job process* killed (`resource_limit`); the API/worker never holds the decoded data and its event loop is never blocked. Verified with a real 96-megapixel RGBA PNG bomb: converts under a generous cap, is stopped under a 1.5 GB cap, and the host keeps working.
3. *Engine limits*: Ghostscript, Poppler, ImageMagick and LibreOffice each start under their own `prlimit` caps (LibreOffice gets a larger address space) with a minimal environment, no shell and a private working directory.
4. *Deadlines*: `JOB_TIMEOUT_SECONDS` is a **whole-job** deadline (earlier it only bounded each engine call, so a 500-page render could have run for hours). Cancellation kills the entire process group, including engines; if the parent (API/worker) dies, the job process notices the closed IPC channel and kills its own group instead of leaving orphans.
5. *Admission control*: per-owner concurrency/quotas are checked and a job slot is **reserved atomically** before the upload is read (a per-owner lock + an `uploading` placeholder), so a burst of parallel uploads cannot exceed the limit; a global `MAX_STORAGE_MB` cap refuses new work with 503 when disk is nearly full.
6. *Recovery*: runners heartbeat every 2 s; a reaper fails jobs whose heartbeat stopped (`worker_lost`) or that nobody picked up (`queue_timeout`); claims are atomic (a job delivered twice runs once).
7. *Deployment hardening*: read-only root filesystems, dropped capabilities, no-new-privileges, pids/memory/CPU limits (compose). For the strongest posture also run workers on a network with no outbound access (documents never need the internet).

**Browser**: a real Content-Security-Policy on the SPA (no inline/eval scripts, no third-party origins, `frame-ancestors 'none'`, `form-action 'self'`, `object-src 'none'`), shared between `vite preview`, the e2e suite and nginx with a test that fails if they drift apart.

**Bugs found by these tests and fixed**: boolean env parsing (`MAINTENANCE_MODE=false` used to mean *true*); a concurrency-limit bypass via parallel uploads; unbounded total job time; a worker that silently never started when the install path contained a space; malformed multipart returning 500; decoder out-of-memory reported as "invalid image"; orphaned engine processes after a worker crash; sign-out that could be skipped by navigating away immediately; text boxes that left an invisible item in undo history.

**Not covered / known limits**: no antivirus scanning of uploads; no seccomp/namespace sandbox beyond rlimits and container settings (a kernel/engine exploit inside LibreOffice or Ghostscript is mitigated, not eliminated — keep them patched and keep workers network-isolated); Node does not enforce per-job disk quota inside the shared volume (the `RLIMIT_FSIZE` cap limits single files, `MAX_STORAGE_MB` limits the total); the per-owner reservation lock is per API process, so across *several API replicas* a burst can overshoot a limit by up to the number of replicas (the daily quota and atomic job claims still hold).

## Phase 8 additions (production hardening)
- **TLS and proxies** (verified with real nginx 1.27 and Caddy 2.8): TLS 1.2/1.3 only; HSTS (2 years) exactly once per response; CSP and browser headers on everything nginx serves itself; no server version; dotfiles refused; API responses never gzip'd (BREACH). A chain of proxies is where security quietly breaks, so it is tested end to end: the client IP survives Caddy and nginx, a spoofed `X-Forwarded-For` is overwritten at the edge, `limit_req` buckets are **per real client** (not one bucket for the proxy: that would let one noisy visitor throttle everyone), and `X-Forwarded-For` is trusted only from private ranges, so never publish the nginx container on a public interface.
- **Logs**: nginx logs `$uri`, never the query string, because download links carry a signed token. Request ids are validated before the API adopts them and echoed back; the metrics endpoint is token-protected and lives on an internal port, not under `/api`.
- **Fail-safe startup**: invalid configuration, missing production secrets, unreachable dependencies and pending/unknown migrations stop the process with one readable line. `node apps/api/dist/doctor.js` checks, before traffic: https URLs, secret strength/placeholders, proxy trust, rate limiting and isolation on, Stripe settings consistent, engines present, **kernel memory limits actually enforced**, storage, MongoDB + migrations, Redis eviction policy.
- **Rollback safety**: migrations are forward-only and recorded; code older than the database refuses to start rather than corrupting data. Migrations are lock-protected and a failing one is retried, not half-applied.
- **systemd hardening** for bare-metal: non-root user, `NoNewPrivileges`, `ProtectSystem=strict`, private `/tmp`/devices, no capabilities, syscall filter, namespaces/realtime/SUID restricted; workers additionally have **no outbound network** except loopback and the addresses you allow. (`MemoryDenyWriteExecute` is deliberately off: V8's JIT needs it.) The units pass `systemd-analyze verify`; their runtime effect must be confirmed on your host.
- **Images**: production dependencies only (no TypeScript, test runners, browsers), non-root user, `tini` as PID 1 (signal forwarding, zombie reaping from engine children), `.dockerignore` keeps `.env`, `.git`, tests and local data out of the build context, read-only root filesystem and dropped capabilities in compose.
- **Backups contain sensitive data** (password hashes, emails, audit log). `backup.sh` writes `0600` files, keeps the database URI out of the process list, verifies a checksum on restore; **encrypt and copy them off-host** (the scripts do not encrypt).
- **Remaining gaps**: no WAF; no antivirus scan of uploads; no seccomp/namespace sandbox for the engines beyond rlimits and container/systemd settings; certificate pinning/CT monitoring not set up; Prometheus alert delivery is yours to configure.

## Phase 9 additions (account hardening)

- **Email confirmation.** Registration emails a single-use link (24 h; only a SHA-256 of the token is stored; a newer link replaces the older one; resend is limited to one per minute). Finishing a password reset also confirms the address, since the reset link went to that inbox. `REQUIRE_VERIFIED_EMAIL=true` stops an unconfirmed address from starting a paid checkout. Nothing else is gated: unconfirmed users can still use the free tools.
- **Two-step sign-in (TOTP, RFC 6238).** Implemented with Node's crypto (no dependency) and checked against the RFC's published test vectors. Setup needs the password; the secret is shown once with a QR code and does nothing until a code from the app proves it works. A correct password then yields only a 5-minute challenge token (its own audience, so it can never act as an access token); no session or cookie exists until the second factor is accepted.
  - *Brute force:* wrong codes count toward the same 5-strike, 15-minute lockout as wrong passwords, on top of the per-IP rate limit.
  - *Replay:* a TOTP time step is accepted once, enforced by an atomic database update, so the same code used in parallel succeeds exactly once. The same holds for recovery codes.
  - *Recovery codes:* 10 random codes (~49 bits each), stored only as hashes, shown once, single-use; regenerating invalidates the old set.
  - *Secrets at rest:* AES-256-GCM, key derived (HKDF) from `TWO_FACTOR_KEY`, or from `JWT_ACCESS_SECRET` if unset. **Set `TWO_FACTOR_KEY` in production:** otherwise rotating the JWT secret makes every authenticator secret undecryptable and locks all 2FA users out. Values are stored as `v2.<key id>.<iv>.<tag>.<ciphertext>`; the key id (an HMAC of a label under the derived key, so it reveals nothing about the key) is authenticated with the message, and legacy `v1` values still open. **Rotation:** `TWO_FACTOR_KEY_PREVIOUS` keeps old secrets readable while the `rotate-2fa` command re-seals them under the new key (compare-and-set per value, verified before writing, idempotent, never prints key material); runbook in OPERATIONS.md. A secret no configured key opens answers `503 two_factor_unavailable` and is logged, never counted as a wrong code.
  - Turning 2FA on or off, and regenerating recovery codes, re-ask for the password (and a code where it matters) and sign every other device out.
- **Security keys (WebAuthn).** A key is a second factor, checked after the password where an authenticator code would be; it never replaces the password. We store only the public key, a signature counter and a name. Adding a key re-asks for the password; **removing one needs the password and a recovery or authenticator code** (a key cannot vouch for its own removal). The first factor on an account issues recovery codes and signs other sessions out, as the authenticator app does.
  - *Challenges:* random, bound to the account and to the ceremony (registration vs sign-in), valid 5 minutes, and consumed by an atomic database update, so a captured response replays to nothing and two parallel uses let exactly one in.
  - *Binding:* the verifier pins the origin(s) and RP ID from `PUBLIC_URL` (`WEBAUTHN_RP_ID` / `WEBAUTHN_ORIGINS` override); a response made for another site is refused, which is the property that defeats phishing relays.
  - *Clones:* if the stored counter and the new one are not both zero, the new one must be higher, otherwise the sign-in is refused and counted as a failure. Many platform passkeys always report 0, for which this check cannot work.
  - *Brute force:* wrong keys count toward the same 5-strike lockout as wrong passwords and codes.
  - *Not verified:* attestation (we accept any authenticator and do not restrict makes or models) and user verification (PIN/biometric is requested when the key can do it but not required).
  - *Operational:* the RP ID is baked into every credential. **Changing the site's domain makes all registered keys unusable**; users then fall back to recovery codes. `doctor` checks that the origin is https (localhost excepted) and that the RP ID matches the host.
  - An administrator 2FA reset also removes all security keys.
- **Devices.** Users can see where they are signed in (browser and OS from the user-agent; no IP address is stored) and sign devices out remotely, individually or all but the current one. The device list never exposes token material.
- **Administrators must use a second step.** While `REQUIRE_ADMIN_2FA` is on (the default in production; off elsewhere unless set) every `/api/admin` request from an administrator with no authenticator app and no security key is refused with `two_factor_required`. The state is read from the database on each request, not from the token, so it applies the moment an account is promoted or loses its factors. They can still sign in and reach their account page to enrol, which is why this is a gate and not a login block. An administrator cannot drop to no factor (turn off the only app, remove the only key); otherwise a hijacked session could switch the protection off. Nobody can reset their own factors through the admin area, so that takes a second administrator. `doctor` warns when the policy is off in production, and the dashboard counts administrators who are not protected yet. Recovery codes alone do not satisfy it. **If the only administrator loses every factor and every recovery code,** nobody can open the admin area: see the break-glass steps in OPERATIONS.md.
- **Admin reset.** For a user who lost both phone and recovery codes, an administrator can turn off their 2FA. It signs them out everywhere and is written to the audit log with the acting admin. **Verify the person's identity first**: this is the account-recovery path an attacker would target, so the UI asks for confirmation.
- **Not done:** passwordless sign-in with passkeys, SMS codes (deliberately omitted: SIM-swap risk), trusted-device "remember me", forcing 2FA for ordinary users, and breach-password checks. 

## Phase 10 additions (teams and shared billing)

- **Model.** A person is in at most one team (enforced by a unique index, so two simultaneous creations leave one). Roles: **owner** (billing, roles, ownership, deleting the team), **admin** (invite members, remove members, rename) and **member** (view). There is no team id in any URL: every action applies to *the caller's own team*, so there is nothing to tamper with, and ids of invitations/members in a request are always scoped to that team (another team's id is a plain "not found").
- **Shared plan.** The team holds its own Stripe subscription (its own customer, `teamId` in the metadata); a member's effective plan is the better of their own and their team's, **computed on every request**. Removing someone, leaving, or the subscription ending takes effect on the very next request, with no token to revoke and nothing to clean up. A team plan can only raise someone's plan, never lower it. Limits stay *per person*: they are not pooled.
- **Invitations.** Email-bound and single-use: the link only works for the signed-in user whose **confirmed** email equals the invited address (a wrong account is told so with a masked hint, and does not burn the invitation). Only a hash of the token is stored; they expire (default 7 days); claiming is atomic, so parallel accepts join exactly once. A pending invitation holds a seat.
- **Seats** come from the team's plan (`TEAM_SEATS_PRO`, `TEAM_SEATS_BUSINESS`; a team that does not pay has one: its owner). Two invitations racing for the last seat are re-counted and the loser backs out, so a team is never oversubscribed. If a subscription lapses, nobody is evicted, but nobody new can be added.
- **Ownership.** Transfer goes to a member with a confirmed email (they take over billing); the former owner becomes an admin. An owner cannot leave, and cannot delete their account while others are in the team: they must transfer or delete the team. Deleting a team cancels its subscription first, and if Stripe cannot be reached the team is kept rather than leaving a subscription nobody can manage.
- All of it is written to the audit log (`team.*`).
- **Not done:** pooled quotas or per-seat Stripe quantities (the team pays a flat plan price), domain-based auto-join, SSO/SCIM, a team activity or usage view, being in several teams at once, and an admin-console view of teams.
